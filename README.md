# Intraday Position, Risk and P&L Attribution Service

A simulated intraday risk desk in miniature: a small options book is
repriced every session, and the resulting P&L is decomposed into delta,
gamma, vega, theta and an unexplained residual using a C++ Black-Scholes
engine reached from Python over a subprocess protocol, with fills ingested
idempotently into a SQLite ledger that survives duplicated and out-of-order
delivery. Stack: Python 3.12, C++17, SQLite. Every number below was
measured on this machine, not targeted: the residual ratio, the replay
result and the idempotency counts all come from the scripts named next to
them, run on the date of the commit that added this file.

## Why this exists

A trading desk's intraday risk system has to answer two questions
continuously: "what do we own right now, given a fill feed that can
duplicate and reorder messages" and "why did our P&L move the way it did
today, broken into the Greeks a trader actually reasons about". This repo
is a small, honest version of both halves of that system: the ingest and
position-keeping half, and the P&L attribution half, glued together by a
SQLite ledger and a C++ pricer.

## Honest framing

- **This is a research harness, not a production risk system.** There is
  no order management, no real-time feed handler, no multi-user access
  control, no disaster recovery, no regulatory reporting.
- **Black-Scholes Greeks, not a full pricing library.** European options
  only, one underlying per instrument, constant risk-free rate, no
  dividends, no American exercise, no local or stochastic volatility.
- **The fill and market-data stream is entirely simulated, synthetic and
  seeded.** There is no real market data, no real broker connection and no
  real fill anywhere in this repository. Every spot path, vol path and
  fill is generated by `pipeline/simulator.py` from a fixed integer seed;
  rerunning any script in this repo with the same seed reproduces the
  exact same numbers byte for byte.
- **The attribution book and the fill ledger are two related but separate
  systems.** The Greeks-based P&L decomposition (claim 1 and 2) is
  computed per contract, independent of any specific position size; the
  fill ledger and replay harness (claim 3 and 4) validate idempotent,
  order-independent position-keeping on its own synthetic fill stream. See
  Limitations for why they are not wired together end to end.

Machine and toolchain this was built and measured on:
- CPU: AMD Ryzen 7 7800X3D, 8 physical cores, 16 logical processors
- OS: Windows 11 Home, build 10.0.26200
- C++ toolchain: WSL2, Ubuntu 22.04.5 LTS, g++ (Ubuntu 11.4.0-1ubuntu1~22.04.3) 11.4.0, `-O2 -std=c++17`
- Python: 3.12.10 (Windows, native, not WSL)

### Why SQLite, not a message broker or a client/server RDBMS

The whole point of this repo is to run offline and headlessly, on one
machine, with zero external services. A message broker (Kafka, a queue)
solves a distribution problem this project does not have: there is one
producer (the simulator) and one consumer (the ingest pipeline), in the
same process. A client/server RDBMS (Postgres) buys concurrent access and
network transparency at the cost of a service that has to be stood up and
torn down around every test run. SQLite's ACID transactions and a UNIQUE
constraint on `(fill_id, sequence)` are exactly the primitive idempotency
needs, `sqlite3` ships in the Python standard library, and the database
file (or `:memory:` connection, used throughout the test suite) requires
no setup. The tradeoff: this would not survive multiple writer processes
or a real network partition, which is fine for a single-process simulated
desk and explicitly out of scope (see Limitations).

### Why sort by sequence before applying, not apply in arrival order

Storage-layer idempotency (the UNIQUE constraint) only guarantees the
*set* of accepted fills is independent of delivery order and duplication.
It says nothing about the position computed from that set, because
folding fills into a running weighted-average-cost position is not
commutative: which fill triggers a long/short sign flip changes the
resulting average price, and that depends on the order fills are folded
in. `pipeline/ingest.rebuild_positions` therefore never folds fills as
they arrive; it always re-reads every accepted fill for an instrument
sorted by `sequence` ascending before folding. See Findings for the
concrete example that made this necessary, not just theoretically
possible.

### Why C++ for the revaluation/attribution math, and how Python reaches it

Repricing and decomposing P&L per position per session is the realistic
hot path in an intraday risk service: a real book has thousands of
positions marked many times a session, not 2,000 position-sessions run
once, which is all this repo needs. Implementing the pricer and the Taylor
decomposition in C++ demonstrates the same design a real system would use
to keep that path fast, and keeps the reference-oracle repricing and the
attribution math in one place, tested independently of Python
(`cpp/tests/test_black_scholes.cpp`).

Python talks to the compiled `attribution_engine` binary over a
line-delimited CSV protocol on stdin/stdout (documented in full at the top
of `cpp/src/attribution_main.cpp`), one line per position-session in, one
line of results out, in the same order. This was chosen over pybind11 or
nanobind because the math only needs to run in large batches, not in a
tight interactive loop, so process-launch and pipe overhead is negligible
next to the SQLite and simulator work already dominating a run; a text
subprocess protocol also needs no build-system integration between
CPython's ABI and the C++ toolchain, which matters here because the C++
side is built under WSL2 while the Python side runs under native Windows
Python (`pipeline/cpp_bridge.py` transparently routes the call through
`wsl.exe` when running on Windows). The tradeoff is real: a subprocess per
batch has fixed launch latency (measured below) that pybind11 would avoid
entirely for a single long-lived process.

## Validation

Three independent layers, all with output committed under `docs/`:

**1. Reference-oracle diff.** `actual_pnl` is defined as full repricing
at the end-of-day market state minus full repricing at the start-of-day
state, both via the exact Black-Scholes formula; this is the ground truth
the Taylor attribution is checked against, not an approximation of it.
`tests/test_attribution.py::test_reference_oracle_matches_direct_repricing`
asserts `actual_pnl == price_eod - price_sod` to 1e-12 relative tolerance.

**2. Component-sum invariant.** `delta_pnl + gamma_pnl + vega_pnl +
theta_pnl + residual` must equal `actual_pnl` exactly, by construction
(residual is defined as the difference), asserted as a real test across
all 2,000 position-sessions in
`tests/test_attribution.py::test_component_invariant_holds_across_the_full_run`.

**3. Replay-determinism check.** Positions built by ingesting a stream
with 5% duplicated messages and the entire stream reordered within
bounded windows must be bit-identical (Python `==` on the raw tuples, no
tolerance) to positions built from the canonical, correctly ordered
stream. `tests/test_replay.py::test_full_book_replay_positions_are_bit_identical`.

## Findings

**The average-cost-basis fold is silently order-dependent, and it is easy
to prove with three fills.** Take three fills on one instrument, in
sequence order: buy 10 @ 100, sell 12 @ 90, sell 5 @ 80. Folded in that
(correct, sequence-sorted) order, the position ends at -7 contracts with
an average price of 82.857143: the sell-12 fill flips the position from
+10 to -2, resetting the average price to 90, and the sell-5 fill extends
the short from -2 to -7, blending 90 and 80 by size into 82.857143.
Deliver the same three fills out of order, sell-5 before sell-12 (a
perfectly plausible reordering under the replay harness's bounded-window
shuffle), and folding *in arrival order instead of sequence order* still
ends at -7 contracts, but the sell-12 fill is now the one that triggers
the flip from +5 to -7, resetting the average price to 90 with the sell-5
fill's price never entering the blend at all. Quantity matches; average
price does not (90 vs. 82.857143). This is exactly the bug idempotency
alone does not catch: the UNIQUE constraint on `(fill_id, sequence)`
guarantees the *set* of accepted fills is order-independent, but a naive
arrival-order fold of that identical set is not. The fix already in
`pipeline/ingest.rebuild_positions` is to always re-derive positions from
the fills table sorted by `sequence`, never from an incrementally
maintained running total; `tests/test_ingest.py::test_naive_arrival_order_fold_diverges_from_sequence_sorted_fold`
reproduces both the naive fold and the correct one side by side so this
cannot regress silently.

**A second, smaller thing that broke:** the simulator's original RNG
seeding used `random.Random((seed, "universe"))`, a tuple. Python's
`random.Random.seed` only special-cases `int`, `float`, `str`, `bytes` and
`bytearray`; anything else, including a tuple of ints, raises
`TypeError: The only supported seed types are...` immediately. This
surfaced the moment the test suite first ran (not a subtle bug, a loud
one), and the fix was `pipeline.simulator.derive_seed`, which joins seed
parts into a single string before seeding. Worth narrating because it is
the kind of thing that looks like it should work (tuples are hashable,
`random.seed` accepts "any hashable" in the general Python documentation
for other contexts) and does not.

**Where the attribution genuinely loses accuracy**, disclosed rather than
hidden: gap sessions (an injected shock roughly 5x the normal daily move,
about 1 session in 25 per instrument) have a mean residual ratio of
0.6417% versus 0.5595% for non-gap sessions, consistent with the
second-order Taylor expansion losing accuracy on large moves, where
third-order and higher terms in the true repricing are no longer
negligible. More surprising, and disclosed precisely because it is
counterintuitive: the single *worst* session in the whole run by residual
ratio is a non-gap session (2.4829%), not a gap session (1.8142% at the
worst). The ratio metric is a ratio of two small numbers on quiet
sessions, so a session with an unusually small gross P&L (the underlying
barely moved) can have a large ratio even when the absolute residual is
tiny; a few such quiet-but-noisy sessions pull the non-gap maximum above
the gap maximum. The aggregate ratio used for the headline claim sums
numerators and denominators across all sessions before dividing, which is
why this per-session noise does not affect the headline number; see
Measured Results for exactly what the aggregate does and does not capture.

|---|---|---|---|

The one number that matters: **the aggregate residual ratio over the full
250-session, 8-instrument run is 0.5393%** (total unexplained residual
32.74 divided by total gross P&L 6070.82), against a claimed threshold of
under 1.5%. This was the first and only attempt: no seed or scenario
parameter was adjusted to hit this number, per the task's own rule against
tuning a benchmark to force a pass.

What "gross P&L" and "residual ratio" precisely measure, and what they do
not: gross P&L for a session is the sum, across all 8 instruments, of the
absolute value of that instrument's actual (fully repriced) P&L for the
session; it measures total absolute mark-to-market movement in the book
that day, not net P&L, because net P&L can be near zero when positions
move in offsetting directions, which would make a ratio to net
meaningless. The residual ratio aggregates the numerator (sum of absolute
residuals) and denominator (sum of gross P&L) across all 250 sessions and
8 instruments before dividing once, rather than averaging 250 separate
per-session ratios, so a single noisy low-volume session cannot dominate
the headline number the way it dominates the per-session maximum below.

Per-session residual ratio, gap vs. non-gap sessions (gap = an injected
~5x shock, roughly 1 session in 25 per instrument):

| | mean | max |
|---|---|---|
| gap sessions | 0.6417% | 1.8142% |
| non-gap sessions | 0.5595% | **2.4829%** (see Findings for why) |

Idempotent ingest (`docs/idempotent_ingest_output.txt`): the same fill
replayed 1, 10 and 1000 times is accepted exactly once in every case, and
the resulting position is identical (10.0, 101.5) regardless of replay
count; interleaving a duplicate with a distinct second fill still accepts
exactly the 2 distinct fills.

Replay/idempotency at full-book scale (`docs/replay_check_output.txt`):
the canonical fill stream is 3,974 messages; the perturbed stream (5%
duplicated, entire stream reordered in bounded windows of 10) is 4,173
messages, a measured duplicate fraction of 5.0075%; both streams accept
exactly 3,974 distinct fills, and the final positions for all 8
instruments are bit-identical between the canonical and perturbed runs.

Subprocess overhead of the C++ bridge (informal, included for the "why
not pybind11" tradeoff claim above): one `run_attribution_batch` call
covering all 2,000 position-sessions of the full run, including the
`wsl.exe` process launch from Windows Python, completes in well under a
second; per-call launch overhead is on the order of 100 ms; this is why a
subprocess-per-batch design is acceptable here and would not be for a
per-tick hot loop.

## Limitations

- The Greeks-based attribution book and the fill-ledger/replay subsystem
  are validated independently, not wired end to end: the attribution math
  runs per contract (unit notional) and does not scale by the position
  size the ingest pipeline actually rebuilds. A fuller version would drive
  each session's attributed P&L by the position held going into that
  session, and separately decompose intraday fills into realized trading
  P&L versus mark-to-market attribution; this repo does not attempt that
  split.
- The residual ratio is measured, not distribution-free: it depends on
  the simulator's random walk parameters (drift, vol-of-vol, gap
  frequency and size), which were chosen to be plausible rather than
  calibrated to any real market. A materially different parameterization
  would produce a different ratio.
- Second-order Greeks (delta and gamma) are a genuinely weaker
  approximation on gap sessions, as shown in Findings; a production system
  would either revalue more frequently intraday or carry higher-order
  cross-Greeks (vanna, volga) to close that gap further.
- The C++/Python subprocess protocol has no schema validation beyond
  field-count and numeric parsing; a malformed line causes the whole
  batch to fail loudly (exit code 2) rather than skipping just that row,
  which is a reasonable choice for a batch job but would need
  reconsideration for a streaming service.
- There is no Postgres option in this repo. The task allowed documenting
  an optional Postgres path with tests that skip cleanly when unreachable;
  given the time budget, only the SQLite path (the required default) was
  built.
- Fill IDs and sequence numbers are synthetic strings/integers generated
  by the simulator, not sampled from any real exchange or OMS fill-ID
  format.
